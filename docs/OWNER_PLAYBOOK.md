# คู่มือคุมโปรเจกต์ด้วย AI สำหรับเจ้าของที่ไม่เขียนโค้ด

## 1. คำศัพท์จำเป็นมาก

| คำ | มันคืออะไร | ทำไมเจ้าของต้องสนใจ | เจ้าของต้องทำอะไร |
|----|-------------|------------------------|--------------------|
| Repository | โฟลเดอร์เก็บโปรเจกต์ | คือที่เก็บไฟล์ทั้งหมด | ไม่ต้องทำ |
| VS Code | โปรแกรมเขียนโค้ด | Cline ทำงานอยู่ในนี่ | เปิดไฟล์ docs ดู |
| Cline | AI ช่วยเขียนโค้ด | ทำงานแทนนักพัฒนา | อนุมัติแผน, ทดสอบ |
| Documentation | สมุดความจำ | เป็น source of truth | อัปเดตเมื่อเปลี่ยน |
| Task | งานแต่ละอย่าง | ทํางานแต่ละอันให้ชัด | บอกให้ AI เข้าใจ |
| Prompt | ข้อความสั่ง | สั่งงานให้ AI | เป็นภาษาคน |
| Plan | ขั้นตอนทำงาน | ต้องเห็นก่อนแก้โค้ด | อ่าน, อนุมัติ |
| Acceptance criteria | เกณฑ์ผ่านงาน | ตัดสินว่าผ่านหรือไม่ | ตรวจเช็ค |
| Test | การลองทำงาน | ต้องลองก่อนบอกผ่าน | ทดสอบด้วยการกด |
| Build | แปลงโค้ดเป็นไฟล์ให้ใช้ | สร้าง .exe ให้ใช้ | อนุมัติ build |
| Bug | ปัญหาให้แก้ | ต้องแก้เพื่อให้ทำงานได้ | แจ้งเจ้าของ |
| Git | ระบบเซฟเวอร์ชั่น | เซฟเกม, ย้อนกลับได้ | อ่าน diff, อนุมัติ commit |
| Commit | จุดเซฟสถานะ | เก็บงานทำแล้ว | อนุมัติก่อน commit |
| Diff | รายการเปลี่ยน | ดูอะไรมาก่อน commit | อ่านเพื่ออนุมัติ |
| Branch | สเตคทดลอง | ทดลองโค้ดใหม่ | ใช้เมื่อจำเป็น |
| Deploy | ให้ผู้ใช้ใช้ | ต้องอนุมัติก่อน | อนุมัติทุกครั้ง |
| Environment variable | ค่าตั้งค่า | ใช้สำหรับ secret/คีย์ | ตั้งผ่าน .env |
| Database migration | การเปลี่ยน schema | เสี่ยงสูญเสียข้อมูล | อนุมัติ + rollback plan |
## 2. วงจรการทำงานปกติหนึ่งงาน

ไอเดีย → CURRENT_TASK.md → Cline วางแผน → เจ้าของอนุมัติแผน → Cline เขียนโค้ด → Cline ตรวจโค้ด → เจ้าของทดสอบ → Cline สรุป + HANDOFF.md → เจ้าของอนุมัติ commit → งานถัดไป

| ช่วง | ใครทำ | เจ้าของต้องทำ | สิ่งที่ดู | Prompt พร้อมก๊อป |
|------|--------|----------------|----------|-----------------|
| 1. ไอเดีย | เจ้าของ | บอกอยากได้อะไร | ความชัดเจน | \"ฉันอยากให้แอป [ทำอะไร]\" |
| 2. ใส่ task | Cline | อนุมัติ task | scope, non-goals | Cline เขียน task ให้ |
| 3. วางแผน | Cline | อ่านและอนุมัติ | ผู้ใช้เห็นอะไร, ความเสี่ยง | \"APPROVE PLAN\" |
| 4. เขียนโค้ด | Cline | ไม่ต้องทำ | - | - |
| 5. ตรวจโค้ด | Cline | ไม่ต้องทำ | - | - |
| 6. ทดสอบ | เจ้าของ | ทดสอบตามขั้นตอน | ผลลัพธ์ที่เห็น | - |
| 7. สรุป | Cline | อ่านและอนุมัติ | สรุป, git diff | \"APPROVE COMMIT\" |
| 8. commit | Cline | อนุมัติ commit | diff เป็นภาษาคน | \"APPROVE COMMIT\" |
| 9. งานต่อไป | - | เลือกงานใหม่ | - | - |

สัญญาณยังไม่ควรไปต่อ: scope ไม่ชัด, ยังไม่เห็นความเสี่ยง, ยังไม่ได้ลองเอง, git diff มีของนอก scope

## 3. คู่มือเริ่มฟีเจอร์ใหม่

1. เจ้าของบอกไอเดีย: \"ฉันอยากให้แอป [ทำอะไร] โดย [วิธี] สำหรับ [ใคร] สำคัญที่สุด [อะไร]\"
2. Cline ตรวจ requirement/decision/backlog เดิม
3. Cline ใส่ CURRENT_TASK.md (Goal, Scope, Non-goals, Acceptance criteria)
4. เปิด New Task ใน Cline: \"อ่าน docs/HANDOFF.md, CURRENT_TASK.md, 04_DECISIONS.md และเอกสารที่เกี่ยวข้องก่อน เริ่มจากสรุปความเข้าใจ แผน ไฟล์ที่จะกระทบ ความเสี่ยง วิธีทดสอบ แล้วรออนุมัติก่อนแก้โค้ด\"
5. เจ้าของอ่านแผน: ดูสิ่งผู้ใช้เห็น, ไม่ทำอะไร, ความเสี่ยง, วิธีทดสอบ
6. อนุมัติ: \"APPROVE PLAN\" | ต้องแก้: \"แก้แผน [ส่วนที่ต้องแก้]\"
7. Cline ทำงาน, รายงาน git diff เป็นภาษาคน
8. ทดสอบตาม Manual Test Steps ที่ Cline ให้
9. ผ่าน: \"APPROVE COMMIT\" | ไม่ผ่าน: บอก Cline ว่าเกิดอะไร

## 4. คู่มือแก้บั๊ก

ข้อมูลที่ต้องเก็บก่อนส่ง Cline:
- กดอะไร
- คาดหวังอะไร
- เกิดอะไรจริง
- ข้อความ error
- เกิดทุกครั้งหรือบางครั้ง
- ภาพหน้าจอ

แบบฟอร์มแจ้งบั๊ก:
`
# Bug report
- สิ่งที่ฉันทำ:
- สิ่งที่คาดหวัง:
- สิ่งที่เกิดขึ้นจริง:
- ข้อความ error:
- เกิดซ้ำได้หรือไม่:
- รูป/ข้อมูลเพิ่มเติม:
`

หลัง Cline แก้: Cline บอก root cause, วิธีทดสอบ → เจ้าของทดสอบ → ผ่าน: \"APPROVE COMMIT\"

## 5. คู่มือทดสอบงาน

- เจ้าของไม่ต้องอ่านโค้ด แต่ต้องตรวจ \"พฤติกรรมที่ผู้ใช้เห็น\"
- วิธีอ่าน Manual Test Steps: ทำตามขั้นตอนทีละข้อ
- บอกผล: \"ผ่าน\" / \"ไม่ผ่าน\" / \"ไม่ตรงใจ\"
- ตัวอย่างข้อความ: \"กดปุ่ม X คาดหวัง Y แต่เกิด Z\"
- แยก: บั๊ก (ทำงานผิด) vs ไม่ถูกใจ (ทำงานตาม spec แต่ต้องการเปลี่ยน)
- กฎ: ห้ามตอบผ่านถ้ายังไม่ได้ลองเอง

## 6. คู่มือปิดงานและเซฟเกมด้วย Git

Git = ระบบเซฟเกม, Commit = จุดเซฟ
- Commit ไม่ใช่ deploy (ไม่ให้ผู้ใช้เห็นทันที)
- ห้าม commit งานที่ยังทดสอบไม่ผ่าน
- ขั้นตอน: ทดสอบผ่าน → \"APPROVE COMMIT\" → Cline diff → Cline commit → HANDOFF.md updated

## 7. คู่มือเริ่มวันใหม่ / New Task / ย้าย AI Chat

1. Cline อัปเดต HANDOFF.md ก่อนจบ
2. เปิด New Task / Chat ใหม่
3. ส่ง prompt: \"อ่าน docs/HANDOFF.md, CURRENT_TASK.md, 04_DECISIONS.md และเอกสารที่เกี่ยวข้องก่อน เริ่มจากสรุปความเข้าใจ แผน ไฟล์ที่จะกระทบ ความเสี่ยง วิธีทดสอบ แล้วรออนุมัติก่อนแก้โค้ด\"
4. เริ่มจาก Exact next task ใน HANDOFF.md

## 8. สิ่งที่ต้องหยุดและถามก่อนเสมอ

| เรื่อง | ทำไมเสี่ยง | เจ้าของต้องอนุมัติ |
|------|------------|-------------------|
| Database migration / ลบข้อมูล | อาจสูญเสียข้อมูล | migration plan + rollback |
| Login / role / permission | ความปลอดภัย | ระบุสิทธิ์ที่เปลี่ยน |
| Payment | เงินจริง | ผ่าน security review |
| API key / secret | หลุดเป็นช่องโหว่ | วิธีจัดการ secret |
| Email/SMS/LINE ส่งผู้ใช้จริง | ผลกระทบต่อผู้ใช้ | เนื้อหา, จำนวน, target |
| Deploy production | ผู้ใช้จริงได้รับผล | ผ่าน release checklist |
| เปลี่ยน dependency หลัก | อาจพัง/ซ้ำ | เพราะอะไร, impact |
| เปลี่ยน architecture | กระทบทั้งระบบ | design doc + review |
| ลบ/ย้ายไฟล์เยอะ | ยาก rollback | scope + backup plan |
| เปลี่ยนข้อมูลผู้ใช้จริง | GDPR, privacy | scope + audit trail |

## 9. สิ่งที่เจ้าของไม่ต้องทำ

- ไม่ต้องอ่านโค้ดเพื่ออนุมัติ
- ไม่ต้องรู้ database schema
- ไม่ต้องเลือก framework
- ไม่ต้องจำ command
- แต่ต้อง: ตัดสินสินเรื่องผู้ใช้, กติกาธุรกิจ, ความสำคัญ, ทดสอบผลลัพธ์
